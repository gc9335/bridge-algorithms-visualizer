# mediumG 与 largeG 无向图桥算法性能分析

本节针对给定无向图文件 `mediumG(1).txt` 和 `largeG.txt`，比较基准算法与高效算法在桥检测任务上的运行表现。用户提到的 `mediumG.tx` 在当前项目目录中对应的实际文件为 `mediumG(1).txt`。

实验于 2026-06-12 重新运行 `analysis/benchmark_runner.exe`，并用 `analysis/plot_bridge_results.py` 与 `analysis/plot_medium_large_focus.py` 生成图表。基准算法采用“逐条删边 + BFS 重新统计连通分量”的方法；高效算法采用“生成森林 + 并查集压缩已处理路径”的方法。

## 结果说明

在 `mediumG(1).txt` 上，两种算法都检测到 `0` 条桥，结果一致。基准算法耗时 `3.181 ms`，高效算法耗时 `0.009443 ms`，加速比约为 `336.85x`。这说明即使在顶点数和边数都不大的给定数据上，避免重复 BFS 仍然能显著减少运行时间。

在 `largeG.txt` 上，图规模达到 `V=1,000,000`、`E=7,586,063`。高效算法耗时 `365.451 ms`，检测到 `8` 条桥，说明该算法可以在百万级顶点、千万级边以内的图上保持可运行性。基准算法没有实际运行，而是被标记为 `baseline_skipped`，原因是它需要对每条边都重新做一次全图连通性遍历，代价过高。

基准算法在 `largeG.txt` 上的理论工作量约为：

```text
E × (V + E)
= 7,586,063 × (1,000,000 + 7,586,063)
≈ 65,134,414,839,969
```

相比之下，高效算法的主要处理量近似为 `V + E = 8,586,063`。两者相差约数百万倍，因此在大图上跳过基准算法是合理的实验设计，不代表高效算法缺少对照结果，而是说明基准算法本身已经不适合该规模。

## 结论

基准算法适合用于小图上的定义验证和正确性对照，但时间复杂度为 `O(E × (V + E))`，图规模稍大后会快速失去可行性。高效算法利用非树边形成的环排除非桥边，并用并查集跳过已经处理过的树路径，整体表现接近线性复杂度 `O(V + E)`。

因此，对于 `mediumG(1).txt`，高效算法在结果一致的前提下获得约 `336.85x` 的加速；对于 `largeG.txt`，高效算法能够在 `365.451 ms` 内完成桥检测，而基准算法因理论工作量过大不再适合作为实际运行方案。实验结果支持在中、大规模无向图桥检测中采用高效算法。
